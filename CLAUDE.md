# coldoutreach: карта проекта

Читайте эту карту первой и открывайте только файлы под задачу. Цифры в таблицах: примерный размер в токенах.

## Что это
1. Клиент и сайт выписок ЕГРЮЛ по ИНН (`egrul_inn_search.py`, `app.py`, `index.html`).
2. Таблица новых компаний `/leads`: название, ФИО директора, почта, ОКВЭД (код, название), источник почты (ЕГРЮЛ или контакты Checko).
3. Рассылка: тексты писем пишут агенты Cowork (файлы `.md` лежат вне репозитория), `compose.py` собирает письма, `mailer.py` отправляет через mail.ru.

Поток рассылки: `leads_<дата>.csv` + файлы агентов `.md` → `compose.py` → `letters_<этап>.csv` → `mailer.py` → mail.ru. Группу письма определяет карта ОКВЭД от агента (`okved-map.md`: решение по смыслу для каждого кода, в том числе «не писать»), иначе таблица классов из файла сегмента (первые два знака кода), иначе запасная группа 12. Коды без решения агента `compose.py` выписывает в `okved_to_classify.md` (папка данных; только коды и названия видов деятельности и сокращения форм организаций): этот файл передают агенту. Форма организации (ООО, МБУ, ПК…) берётся из начала названия; пока агент не решил иначе (раздел `## Формы` в `okved-map.md`), пишем только ООО. У запасной группы и групп без своего текста может быть свой шаблон письма целиком (заголовки «Письмо 1. Запасной шаблон» и т. п. в файле писем). Этап 1 можно пройти кнопкой «Отправить» на `/leads` (`send_service.py`): таблица сама пишется в папку данных `OUTREACH_DATA`, в таблице выгрузки три колонки «Первое письмо», «Дожим», «Закрывающее» (да или нет, по журналам `letters_N.sent.json`; `leads.table_rows`, `leads.refresh_table`), строки с ушедшим письмом на странице залиты жёлтым до колонки последнего ушедшего письма. Страница показывает таблицу только за выбранную дату (`LeadsJob.status(day)`, запрос `?date=`); дата идёт и в скачивание, и в «Отправить». Журнал `letters_<этап>.sent.json` (статус, время, тема, группа, источник адреса). Этапы 2 (дожим) и 3 (закрывающее) строятся по журналам. Порядок работы для владельца: `LOCAL.md`, раздел «Рассылка».

## Как пользоваться рассылкой (напоминать владельцу по его просьбе)
Когда владелец спрашивает, как пользоваться рассылкой, в каком порядке всё делается, когда решает агент («напомни порядок», «как это работает»), перескажите эти шаги простыми словами, как для первокурсника, и добавьте, что из этого уже сделано и что дальше. Порядок утверждён владельцем (2026-10-11):

1. Вы говорите дирижёру «хочу рассылку», он запускает сайт.
2. Вы вставляете текст с Checko, сайт собирает таблицу. Агентов тут нет.
3. Вы говорите «отправить сообщения». Дирижёр запускает проверку (или вы нажимаете «Отправить», окно покажет то же самое). Программа смотрит на каждую компанию: какая форма и какой вид деятельности. Что знает по решениям агента, применяет. Что не знает, записывает в файл `okved_to_classify.md`. Письма пока не уходят.
4. Здесь решает агент. Дирижёр отдаёт файл агенту, тот возвращает решения. Это делается один раз на каждый новый код или форму, дальше всё запоминается.
5. Программа собирает письма заново по решениям агента, вы видите окно «Что будет отправлено», подтверждаете, и письма уходят.

Пояснение для владельца: программа как сортировщик на складе со справочником. Чего в справочнике нет, она кладёт на стол «вопросы эксперту», эксперт (агент) решает и вписывает в справочник. Агент сам не включается, его запускает дирижёр на шаге 4; если шаг пропустить, программа работает по старым правилам (пишет только ООО, группа по первым двум знакам кода) и предупреждает строкой в окне. Пока владелец не утвердил запасной шаблон письма, в группы без своего текста письма не отправляются (галочку «запасной вариант» не ставить).

## Тесты
Папка `tests/`, по файлу на модуль (`tests/test_mailer.py`, `tests/test_compose.py`, ...). Читайте только тест того модуля, который меняете. Запуск всего: `python -m unittest discover -q` (около 300 тестов, 35 секунд). Тесты не должны трогать настоящие `local.env` и `settings.json` (передавайте временные пути).

## Правила
- **Правки ушли в git: всегда говорите владельцу, что проект в PyCharm нужно обновить, и давайте краткие шаги.** Название ветки сессии каждый раз новое, поэтому называйте её. Шаги: 1) остановить сайт (красный квадрат в окне Run); 2) **Git → Fetch**; 3) внизу справа нажать на название ветки → **Remote Branches** → `origin/<ветка>` → **Checkout** (если ветка у владельца уже та же: **Git → Update Project**, Ctrl+T); 4) если PyCharm скажет про изменённые файлы, выбрать *Smart Checkout*, не *Force*; 5) запустить `run_local` заново. Если правка меняла `requirements.txt`, добавить в Terminal `pip install -r requirements.txt`. `local.env` и папка данных в git не лежат, при смене ветки они остаются на месте. Если правка касалась файлов агентов (их нет в git), скажите, что именно передать дирижёру.
- `mailer.py`, `compose.py` и `mailing/` работают на одной стандартной библиотеке (без pip): их копируют на другие машины.
- Корень проекта хранит `local.env` (пароль, ссылка на форму, пути к файлам агентов) и `settings.json` (лимит с сайта); оба вне git. Пути к ним задаёт `mailing/config.py`.
- Репозиторий публичный: адреса, ФИО, пароли, журналы и тексты агентов в него не попадают (см. `.gitignore`). В сообщениях программ адреса при необходимости скрываются (`--mask-addresses`, `--background`).
- Письма не подставляют ФИО и названия компаний; нет ссылки на форму (или подписи, если в шаблоне есть `{{подпись}}`) - письма не собираются.
- Интерфейс для владельца: команды `python compose.py ...`, `python mailer.py ...`, `python run_local.py` и тексты в `LOCAL.md` не менять без причины: на них опираются инструкции агентов.
- Сообщения программ и документы на русском. Windows и PyCharm у владельца: проверяйте код, зависящий от ОС (процессы, пути).
